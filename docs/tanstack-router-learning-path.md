## Level 0: Web basics (URLs, routes, pages, slugs)

### The parts of a URL

```
https://app.example.com/w/acme-construction/projects/42?tab=documents&page=2#notes
└──────────┬──────────┘└──────────────┬───────────────┘└─────────┬─────────┘└──┬─┘
       domain                      path                  search params      hash
```

| Part              | Example                            | Used for                                               |
| ----------------- | ---------------------------------- | ------------------------------------------------------ |
| **Path**          | `/w/acme-construction/projects/42` | **Which** page and **which** item                      |
| **Search params** | `?tab=documents&page=2`            | **How** to show it: tab, filters, sorting, page number |
| **Hash**          | `#notes`                           | Scrolling to a section of the page                     |

### Route vs page

- A **route** is a rule: "URLs that look like this show this component". In TanStack Router, each file in `src/routes/` is a route, for example `posts/$postId.tsx` matches `/posts/<anything>`.
- A **page** is what the user sees on screen: the route's component, rendered inside its layouts, filled with data.

One route can produce many pages. `posts/$postId.tsx` is one file, but `/posts/1`, `/posts/2` and `/posts/42` are three different pages, because each loads a different post.

|            | Route                       | Page                               |
| ---------- | --------------------------- | ---------------------------------- |
| What it is | A URL pattern + a component | The result on screen               |
| Example    | `/posts/$postId`            | `/posts/42`, showing post 42       |
| How many   | One file                    | As many as there are matching URLs |

### Params, ids and slugs

A `$` segment in a route is a **dynamic param**: a placeholder filled from the URL and read with `Route.useParams()`.

```
Route file:  posts/$postId.tsx
URL:         /posts/42
Params:      { postId: '42' }
```

The value in that segment is usually one of two things:

- An **id**: the item's database identifier, such as `42` or `8f3a2c91-4b7e-...`.
- A **slug**: a readable, URL-friendly version of the item's name, such as `acme-construction`.

| Name               | Slug                 |
| ------------------ | -------------------- |
| Acme Construction  | `acme-construction`  |
| Bâtiment Nord 2026 | `batiment-nord-2026` |
| My First Post!     | `my-first-post`      |

A slug is made by lowercasing the name, replacing spaces with `-`, and removing accents and special characters. It must be unique so the backend can find the item with it, for example with `getBySlug(params.slug)`.

To the router, a slug is just another param: `$slug`, `$workspaceSlug` and `$postId` all work the same way. The name only tells developers what kind of value to expect.

### Can the page change without the URL changing?

Yes. Anything stored in React state (`useState`) changes the screen without touching the URL: opening a modal, switching a tab, typing in a search box, going to the next page of a list.

The catch is that this state is lost on refresh, and a copied link doesn't include it.

| What changes   | Stored in     | Survives refresh and shareable? | Example                              |
| -------------- | ------------- | ------------------------------- | ------------------------------------ |
| Which item     | Path param    | Yes                             | `/posts/42` → `/posts/43`            |
| How it's shown | Search params | Yes                             | `?tab=documents` → `?tab=rules`      |
| Temporary UI   | React state   | No                              | An open dropdown, a half-filled form |

**Rule of thumb:** if a user would expect a link or the Back button to bring them back to the same view, put it in the URL (a path param or a search param). Otherwise, keep it in React state.

`PaginationExample` is an example of the third row: the page number lives in `useState`, so a refresh always goes back to page 1. Level 4 moves it into `?page=2`.

## Level 1: The basics

| Concept                         | What it is                                                                                                                                                | Docs                                                                                                               |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| **Router and `RouterProvider`** | `createRouter({ routeTree })` creates the router, and `<RouterProvider>` renders it                                                                       | [Quick start](https://tanstack.com/router/latest/docs/framework/react/quick-start)                                 |
| **Type registration**           | `declare module '@tanstack/react-router' { interface Register { router: typeof router } }` makes every link and param type-safe                           | [Type safety](https://tanstack.com/router/latest/docs/framework/react/guide/type-safety)                           |
| **Root route**                  | `__root.tsx`, the layout that wraps every page. Created with `createRootRoute`, or `createRootRouteWithContext` when routes need shared context (Level 5) | [Routing concepts](https://tanstack.com/router/latest/docs/framework/react/routing/routing-concepts)               |
| **File-based routing**          | Each file in `src/routes/` is a route, and `routeTree.gen.ts` is generated from them                                                                      | [File-based routing](https://tanstack.com/router/latest/docs/framework/react/routing/file-based-routing)           |
| **`createFileRoute`**           | How each route file declares its route id and component. The plugin writes and updates the id for you                                                     | [Routing concepts](https://tanstack.com/router/latest/docs/framework/react/routing/routing-concepts)               |
| **`<Outlet />`**                | Where child routes render inside a parent layout                                                                                                          | [Routing concepts](https://tanstack.com/router/latest/docs/framework/react/routing/routing-concepts)               |
| **Index routes**                | `index.tsx` matches the parent path exactly, such as `/`                                                                                                  | [File naming conventions](https://tanstack.com/router/latest/docs/framework/react/routing/file-naming-conventions) |

The setup in `main.tsx`:

```tsx
const router = createRouter({ routeTree, context: { auth } })

declare module '@tanstack/react-router' {
  interface Register {
    router: typeof router
  }
}

createRoot(document.getElementById('root')!).render(
  <StrictMode>
    <QueryClientProvider client={queryClient}>
      <RouterProvider router={router} />
    </QueryClientProvider>
  </StrictMode>,
)
```

What each piece does, and how to see it:

- **Type registration:** a `<Link to="/contact">` to a route that doesn't exist is a TypeScript error. Comment out the `declare module` block and the error disappears, because TypeScript no longer knows your routes.
- **File-based routing:** create an empty file in `src/routes/` while `npm run dev` runs. The plugin fills it with a `createFileRoute(...)` and adds the route to `routeTree.gen.ts`. Rename the file and the plugin updates the id.
- **`routeTree.gen.ts`:** generated, so it's excluded from ESLint and Prettier and never edited by hand. If the editor shows a stale "not assignable to `keyof FileRoutesByPath`" error after moving files, keep the dev server running or restart the TypeScript server.

## Level 2: Navigation

| Concept                           | What it is                                                                                                                                     | Docs                                                                                               |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| **`<Link>`**                      | Type-safe links. The active link gets `data-status="active"`, and `activeOptions` controls when a link counts as active                        | [Navigation](https://tanstack.com/router/latest/docs/framework/react/guide/navigation)             |
| **`useNavigate()`**               | Navigating from code, for example after a form submit                                                                                          | [Navigation](https://tanstack.com/router/latest/docs/framework/react/guide/navigation)             |
| **`<Navigate>` and `redirect()`** | Redirecting in a component or inside a route (`throw redirect(...)` in `beforeLoad`)                                                           | [Navigation](https://tanstack.com/router/latest/docs/framework/react/guide/navigation)             |
| **Not found**                     | Unknown URLs show the router's default "Not Found" text inside the root layout. `notFoundComponent` replaces it with a custom page when needed | [Not found errors](https://tanstack.com/router/latest/docs/framework/react/guide/not-found-errors) |

**`<Link>` vs `useNavigate()`:** use `<Link>` whenever the user clicks to go somewhere. It renders a real `<a href>`, so Cmd+click, "open in new tab", "copy link", keyboard and screen readers all work. Use `useNavigate()` only for navigation triggered by code, such as after a form submit.

```tsx
<Link to="/posts/$postId" params={{ postId: String(post.id) }}>
  {post.title}
</Link>
```

**Active links:** the navbar styles `.nav-link[data-status='active']`, which `<Link>` sets on its own. Home needs `activeOptions={{ exact: true }}`, otherwise `/` counts as active on every page, because every path starts with `/`.

**Links take URLs, not route ids:** `<Link to="/profile">` is correct. `<Link to="/_account">` is a type error, because a pathless route has no URL (Level 3).

## Level 3: Route structure

These file-naming rules come from the [file naming conventions](https://tanstack.com/router/latest/docs/framework/react/routing/file-naming-conventions) page.

| Convention                         | Example in this repo                      | Meaning                                                          |
| ---------------------------------- | ----------------------------------------- | ---------------------------------------------------------------- |
| **Nested routes** (folders or `.`) | `posts/route.tsx` + `posts/index.tsx`     | `/posts` is a layout, and child pages render in its `<Outlet />` |
| **Dynamic params** (`$`)           | `posts/$postId.tsx`                       | `/posts/42`, read with `Route.useParams()`                       |
| **Pathless layouts** (`_` prefix)  | `_auth.tsx`, `_account.tsx`               | A shared layout that doesn't add anything to the URL             |
| **Route groups** (`(folder)`)      | `(authentication)/login.tsx`              | Organizes files without changing the URL or adding a layout      |
| **Excluded files** (`-` prefix)    | `-components/PostCard.tsx` (not done yet) | Keeps helper files next to routes without making them routes     |

### Layout routes, index routes and `<Outlet />`

In a route folder, `route.tsx` and `index.tsx` play different roles:

```
src/routes/_auth/posts/
├── route.tsx      # /posts         layout for the whole section
├── index.tsx      # /posts/        page shown at exactly /posts
└── $postId.tsx    # /posts/$postId page shown at /posts/1, /posts/42, ...
```

| File                | Role                                                                               | Renders on                          |
| ------------------- | ---------------------------------------------------------------------------------- | ----------------------------------- |
| `posts/route.tsx`   | **Layout**: what every page of the section shares (title, sub-navigation, sidebar) | `/posts` **and** every URL under it |
| `posts/index.tsx`   | **Index page**: the section's home                                                 | Only on exactly `/posts`            |
| `posts/$postId.tsx` | **Child page**: one post                                                           | Only on `/posts/<id>`               |

`posts/route.tsx` is the folder version of `posts.tsx`: both create the `/posts` layout. The index route's id is written `'/posts/'`, with a trailing slash, which means "the index of `/posts`".

**`<Outlet />`** is a placeholder inside a layout. The router replaces it with the child route that matches the current URL:

```
URL: /posts                         URL: /posts/42
┌─ __root.tsx ───────────────┐      ┌─ __root.tsx ───────────────┐
│ ┌─ _auth.tsx ────────────┐ │      │ ┌─ _auth.tsx ────────────┐ │
│ │ navbar                 │ │      │ │ navbar                 │ │
│ │ ┌─ posts/route.tsx ──┐ │ │      │ │ ┌─ posts/route.tsx ──┐ │ │
│ │ │ section header     │ │ │      │ │ │ section header     │ │ │
│ │ │ ┌─ <Outlet /> ───┐ │ │ │      │ │ │ ┌─ <Outlet /> ───┐ │ │ │
│ │ │ │ posts/index    │ │ │ │      │ │ │ │ posts/$postId  │ │ │ │
│ │ │ └────────────────┘ │ │ │      │ │ │ └────────────────┘ │ │ │
│ │ └────────────────────┘ │ │      │ │ └────────────────────┘ │ │
│ └────────────────────────┘ │      │ └────────────────────────┘ │
└────────────────────────────┘      └────────────────────────────┘
```

- The layouts stay the same, and only the content of the innermost `<Outlet />` changes.
- Each layout level needs its own `<Outlet />`: `__root.tsx` shows `_auth.tsx`, `_auth.tsx` shows `posts/route.tsx`, and `posts/route.tsx` shows `index.tsx` or `$postId.tsx`.
- Without an `<Outlet />`, a layout still renders, but its child pages have nowhere to appear.

**Fixed vs dynamic segments:** `posts/post.tsx` would match only the exact URL `/posts/post`. `posts/$postId.tsx` matches any value in that position.

### Pathless layouts (`_` prefix)

A pathless layout wraps its child pages in shared UI or logic **without adding anything to the URL**. The layout file has the same name as the folder, next to it:

```
src/routes/_auth/
├── _account.tsx          # layout: left panel + <Outlet /> + right panel
└── _account/
    ├── profile.tsx       # /profile   (not /_account/profile)
    └── settings.tsx      # /settings
```

- Every route inside `_account/` renders inside `_account.tsx`, at any depth. Routes outside the folder (`about.tsx`, `posts/`) don't get the panels. To choose which pages get a layout, move their files into or out of its folder.
- The names must match exactly: `_account.tsx` is the layout for `_account/`.
- When you navigate between children, only the `<Outlet />` content changes. The layout stays mounted, so its state is kept (scroll position, open menus, loaded data).
- This repo uses two pathless layouts: `_auth` for the login check and navbar, and `_account` for the account panels.

**Route id vs URL:**

|              | Value                     | Used in                                                             |
| ------------ | ------------------------- | ------------------------------------------------------------------- |
| Route **id** | `/_auth/_account/profile` | `createFileRoute('/_auth/_account/profile')`, written by the plugin |
| **URL**      | `/profile`                | `<Link to="/profile">`, the address bar                             |

A pathless route has no URL of its own, so you can only link to the pages inside it. A side effect: the navbar's Account link (to `/profile`) is not active on `/settings`, because the two URLs share no prefix.

**Can profile and settings have a parent page?** They already share a parent **layout** (`_account.tsx`). A parent **page with its own URL**, such as `/account`, needs a normal folder instead:

```
src/routes/_auth/account/
├── route.tsx      # /account           layout (panels + <Outlet />)
├── index.tsx      # /account           parent page, or a redirect to /account/profile
├── profile.tsx    # /account/profile
└── settings.tsx   # /account/settings
```

To skip the overview page, redirect from the index route:

```tsx
export const Route = createFileRoute('/_auth/account/')({
  beforeLoad: () => {
    throw redirect({ to: '/account/profile' })
  },
})
```

### Route groups (`(folder)`)

A folder in parentheses only organizes files. It adds nothing to the URL and no layout:

```
src/routes/(authentication)/
├── login.tsx      # id: /(authentication)/login     URL: /login
└── register.tsx   # id: /(authentication)/register  URL: /register
```

Moving a file into or out of a group changes only its route id. The URL, the parent layout and every `<Link>` stay the same. An empty group folder is ignored by the router (and by git).

### Which folder type to use

| Folder   | Example                      | Adds to URL?       | Adds a layout? | Use it for                                                         |
| -------- | ---------------------------- | ------------------ | -------------- | ------------------------------------------------------------------ |
| Normal   | `posts/` + `posts/route.tsx` | Yes (`/posts/...`) | Yes            | A section with its own URL                                         |
| Pathless | `_auth/` + `_auth.tsx`       | No                 | Yes            | Shared UI or logic across unrelated URLs: an auth guard, a sidebar |
| Group    | `(authentication)/`          | No                 | No             | Organizing files only                                              |

They nest freely. In this repo, `_account` is a pathless layout inside the `_auth` pathless layout, and `posts/` is a normal folder inside `_auth`.

## Level 3b: Reading real-world route structures

Large apps combine all the Level 3 conventions, which makes file names look cryptic at first. Four more things help you read them.

### 1. Non-nested routes (`_` suffix)

A trailing `_` on a segment keeps the URL nested but **not** the layout. See [non-nested routes](https://tanstack.com/router/latest/docs/framework/react/routing/routing-concepts).

| File                              | URL                  | Renders inside                             |
| --------------------------------- | -------------------- | ------------------------------------------ |
| `dashboard.tsx`                   | `/dashboard`         | The parent layout                          |
| `dashboard.reports.tsx`           | `/dashboard/reports` | `dashboard.tsx`'s `<Outlet />`             |
| `dashboard_.w.$workspaceSlug.tsx` | `/dashboard/w/acme`  | The parent layout, **not** `dashboard.tsx` |

Use it when a URL belongs under a section but the page needs its own full layout.

### 2. Mixing folders and dotted file names

Folders and dots mean the same thing, so a route can be split across both. A route file next to a folder with the same name is the layout, and the folder holds its children:

```
routes/
├── _auth.tsx                  # pathless layout (an auth guard)
└── _auth/                     # children of _auth.tsx
    ├── _sidebar.tsx           # pathless layout nested inside _auth
    ├── _sidebar.settings.tsx  # /settings, inside both layouts
    ├── w.$slug.tsx            # /w/$slug, a layout for one workspace
    └── w.$slug/
        └── projects.$projectId.tsx  # /w/$slug/projects/$projectId
```

Group folders like `(general)` or `(sidebar)` can be added anywhere for organization; they never change the URL or the nesting.

**How to read any file name:**

1. Join the folders and the file name with `/` in place of every `.`.
2. Drop `(group)` segments and `_pathless` segments to get the **URL**.
3. Each `_pathless` segment or parent route that has its own file is a **layout** the page renders inside.
4. When in doubt, open `routeTree.gen.ts`: each route lists its `fullPath` (the URL) and its `parentRoute` (the layout it renders in).

### 3. Checking the current route with `useMatchRoute()`

Layouts sometimes need to know which child page is showing, for example to collapse a sidebar on one page. [`useMatchRoute`](https://tanstack.com/router/latest/docs/framework/react/api/router/useMatchRouteHook) returns a function that checks a route against the current location:

```tsx
const matchRoute = useMatchRoute()
const isLibrary = !!matchRoute({ to: '/library' })
```

### 4. Ignoring non-route files in `src/routes`

The `-` prefix excludes single files. To exclude a whole kind of file, such as translations stored next to each route, set [`routeFileIgnorePattern`](https://tanstack.com/router/latest/docs/api/file-based-routing) in the Vite plugin:

```ts
tanstackRouter({
  target: 'react',
  autoCodeSplitting: true,
  routeFileIgnorePattern: '.i18n', // about.i18n.ts is not treated as a route
})
```

## Level 3c: Protecting routes with authentication

All the protected pages live inside the pathless `_auth` layout. Its `beforeLoad` runs **before** the route and all its children load, so protected pages never render for a visitor who isn't logged in, not even briefly. See [authenticated routes](https://tanstack.com/router/latest/docs/framework/react/guide/authenticated-routes).

This section previews three concepts covered properly later: router context (Level 5), `beforeLoad` (Level 5) and `validateSearch` (Level 4).

### The flow

```
Visitor opens /posts
   ↓
_auth.tsx → beforeLoad: is there a logged-in user?
   ├─ no  → redirect to /login?redirect=/posts
   │          ↓ submit the form
   │        auth.login(name) → router.invalidate() → back to /posts
   └─ yes → render the navbar + <Outlet /> → /posts
```

1. **Not logged in:** `_auth`'s `beforeLoad` throws a redirect to `/login`, with the requested page in `?redirect=`.
2. **Login:** the form saves the user, `router.invalidate()` re-runs the route checks, and `router.history.push(redirectTo)` returns to the requested page.
3. **Already logged in and opening `/login`:** the login route's own `beforeLoad` redirects into the app.
4. **Log out:** `auth.logout()` then `router.invalidate()`. `_auth`'s `beforeLoad` runs again, finds no user and redirects to `/login`.

### The four pieces

**1. Auth store** (`src/auth.ts`), a fake one for learning:

```ts
const KEY = 'auth-user'

export type AuthUser = { name: string }

export const auth = {
  getUser: (): AuthUser | null => {
    const raw = localStorage.getItem(KEY)
    return raw ? JSON.parse(raw) : null
  },
  login: (name: string) => localStorage.setItem(KEY, JSON.stringify({ name })),
  logout: () => localStorage.removeItem(KEY),
}

export type Auth = typeof auth
```

**2. Router context**, so every route can use `auth`:

```tsx
// main.tsx
const router = createRouter({ routeTree, context: { auth } })

// __root.tsx
export const Route = createRootRouteWithContext<{ auth: Auth }>()({
  component: RootComponent, // only <Outlet /> + devtools
})
```

Routes read it as `context.auth` in `beforeLoad` and with `Route.useRouteContext()` in components.

**3. The guard** (`src/routes/_auth.tsx`):

```tsx
export const Route = createFileRoute('/_auth')({
  beforeLoad: ({ context, location }) => {
    if (!context.auth.getUser()) {
      throw redirect({ to: '/login', search: { redirect: location.href } })
    }
  },
  component: AuthLayout, // navbar + Log out button + <Outlet />
})
```

The navbar lives here, not in `__root.tsx`, so the login page doesn't show the app's navigation.

**4. The login page** (`src/routes/(authentication)/login.tsx`):

```tsx
export const Route = createFileRoute('/(authentication)/login')({
  validateSearch: (search) => ({
    redirect:
      typeof search.redirect === 'string' && search.redirect.startsWith('/')
        ? search.redirect
        : '/',
  }),
  beforeLoad: ({ context, search }) => {
    if (context.auth.getUser()) throw redirect({ href: search.redirect })
  },
  component: LoginPage,
})
```

The `startsWith('/')` check prevents an **open redirect**: without it, a link like `/login?redirect=https://evil.com` would send users to another website after logging in.

### Frontend guard vs real security

A frontend guard only controls what the user **sees**. Anyone can set `auth-user` in `localStorage` or call the API directly. Real protection must live in the backend: with NestJS, a guard that checks a token or session cookie on every protected API route. To connect a real backend, replace the body of `auth.ts` with API calls; the routes don't need to change.

## Level 4: Search params

This is TanStack Router's signature feature. The docs describe it as "`useState` right in the URL". The login page already uses a simple version for `?redirect=`.
